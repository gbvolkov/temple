### GAP-01 — миграционная приёмка не завершена

**Приоритет:** P0, блокирует завершение содержательной миграции и массовую публикацию архива.

После применения schema 13 подготовленная копия ожидаемо содержит 1 757 таких флагов: migration `revert_accidental_publication` переводит известную случайно опубликованную запись `660f8f7c-1183-464d-b39c-f4df2579fd45` из `published`, version 7, flag 0 в `draft`, version 8, flag 1. Raw-источник при этом не изменяется.

Исходный audit до автоматической подготовки содержал:

- 1 470 блокирующих проблем;
- 3 048 предупреждений;
- 1 757 информационных отметок.

**Риск:** непроверенный архив нельзя безопасно публиковать, хотя технический cutover уже завершён.

**Автоматически выполнено:** schema 14, contract 1.1, rules 1.2.0, preview/apply/post-audit/verify/rollback, recovery, external evidence, generated-media provenance, полное досье и ролевой UI. ### CMS-02 — пустые блоки ломают preview

**Приоритет:** P1.

Добавление изображения, галереи, видео, файла и ряда других пустых блоков немедленно отправляет невалидный payload. Сервер отвечает 422, preview показывает технический JSON `{"detail":"Блок …"}`, консоль засоряется повторными ошибками.

**Что сделать:** не отправлять preview для локально неполного блока; показывать inline-ошибку возле карточки; сохранять последний успешный preview; не выводить raw JSON.

**Критерий:** добавление пустого блока не создаёт console error и не уничтожает предыдущий preview.

### CMS-03 — рассинхронизация фильтра chooser медиатеки

**Приоритет:** P1.

После выбора `usage=used`, закрытия и повторного открытия chooser UI показывает **«Любое»**, но запрос остаётся `/api/admin/media?...&usage=used`. В результате отображается «Файлы не найдены» при наличии подходящего файла.

Причина в `openMediaChooser`: DOM-значения очищаются, но `state.media.q` и `state.media.usage` не сбрасываются.

**Что сделать:** атомарно сбрасывать DOM и state или сохранять оба значения намеренно; добавить E2E на close/reopen.

### CMS-04 — отозванная сессия не возвращает вход

### CMS-12 — race при обновлении migration dashboard

**Приоритет:** P2.

`refreshMigrationStatus()` запускает параллельно status/issues/batches, но не отменяет предыдущий refresh и не проверяет sequence. При быстром изменении нескольких фильтров более поздний ответ старого запроса может перерисовать выдачу после нового.

**Исправление:** предыдущий refresh отменяется через `AbortController`, sequence ID запрещает устаревшему ответу перерисовать экран, а фильтр получает согласованные busy/disabled-состояния. E2E искусственно переставляет ответы и подтверждает latest-only rendering.

## Исправлено на этапе 5

### GAP-02 — реестр потерянных медиа не был связан с панелью

**Исходный факт:** отчёт и manifest содержали 201 URL отсутствующих legacy-файлов, а немигрированная рабочая БД ещё не имела актуальной таблицы проблем и показывала ноль.

**Исправление:** идемпотентная сверка на мигрированной SQLite-копии импортирует отчёт в `missing_media_issues`, восстанавливает связи с материалами и сравнивает URL отчёта, manifest и очереди CMS. ### GAP-03 — расхождение числа медиа

**Исходный факт:** исследовательский reindex 21 июля обработал 13 701 физический файл, а отчёт сообщал о 13 746 зеркалированных URL.

**Причина:** 13 746 — число URL manifest, а не уникальных файлов. 48 URL являются алиасами уже сохранённых объектов, поэтому manifest соответствует 13 698 уникальным оригиналам. Reindex считает физические файлы и дополнительно включает CMS-загрузки вне manifest. На актуальном source fingerprint находятся 13 699 физических файлов: 13 698 manifest-оригиналов и одна самостоятельная CMS-загрузка; отсутствующих manifest-файлов нет. Историческое наблюдение 13 701 арифметически соответствует тому снимку каталога с тремя файлами вне manifest. Поскольку пофайловый fingerprint того прогона не сохранялся, имена двух отсутствующих сейчас объектов доказательно восстановить нельзя; старое число не используется как новый baseline.

**Исправление:** итог каждой фоновой переиндексации сохраняет и показывает manifest URL, уникальные файлы, алиасы, физические и несвязанные файлы, производные, отсутствующие оригиналы, ссылки материалов и необъяснённые проблемы. Source-data тест фиксирует обе контрольные формулы и нулевую потерю.

### CMS-20 — `verify` не является fail-closed semantic gate

**Исторический приоритет:** P0.

**Шаги воспроизведения:** выполнить тот же source-data workflow, затем запустить `verify_preparation` после завершённого post-apply audit.

`technical_blocker`. Теперь только зеркальные static GIF внутри `legacy/` проходят
Pillow-верификацию и индексируются как `image/gif`, `ready`; пользовательская загрузка
GIF остаётся запрещённой. Анимированные и повреждённые GIF по-прежнему fail-closed.

### CMS-27 — корректное legacy-изображение с исторически неверным расширением считалось invalid

**Исторический приоритет:** P1.

Production reconciliation выявил один публичный файл: URL и manifest называли
его `.jpg`, но проверенные байты являлись PNG 300×26 с корректным SHA-256.
Теперь для зеркальных JPG/PNG/WebP индексатор доверяет проверенному формату
байтов, сохраняет MIME `image/png` и provenance исходного/обнаруженного
расширения. Пользовательская загрузка остаётся строгой и тот же mismatch
отклоняет.

### CMS-28 — clean bootstrap пропускал media reconciliation warning

**Исторический приоритет:** P0.

Первый успешный cutover дошёл до активации при `status=warning`,
`invalid_files=1`, `unexplained_count=1`, поскольку новый bootstrap сохранял
отчёт, но не проверял его результат. Теперь до активации и при каждой
post-activation проверке обязательно выполняется reconciliation и требуется
одновременно `status=ok` и `unexplained_count=0`.

## Исправлено на этапе 6

### CMS-18 — ложный дубль cover и первой фотографии

**Исходный факт:** аудит объединял ссылки из разных семантических полей и создавал `duplicate_media_reference`, когда обложка галереи намеренно совпадала с первой фотографией.

### Автоматическая подготовка миграции

Добавлены детерминированные правила структурной очистки, защищённый preview/apply с повторной проверкой version/hash, системные ревизии, компенсирующий rollback, фоновые задачи, роли, UI-досье и фильтрация. Apply не публикует материалы, не меняет workflow-статусы и не снимает `migration_review_required`.

## Рекомендуемый порядок исправления

1. Редактору подтвердить актуальность страницы треб, затем publisher/admin публикует её обычным workflow.
2. Завершить содержательную часть `GAP-01` редакционными партиями (этапы 7–8).
3. После каждой партии повторять audit и semantic verify по нормативной инструкции.

## Минимальные release-критерии

- нет тихой потери dirty-форм;
- 401 всегда приводит к понятному повторному входу;
- account actions доступны на mobile;
- preview не показывает raw JSON;
- chooser state и UI совпадают;
- migration audit/pilot имеют управляемый status/error flow;
- список missing media согласован с миграционным отчётом;
- у публикуемых материалов нет blocker и незаполненных required;
- backup/restore drill и production smoke пройдены.
