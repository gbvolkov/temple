# Полное описание решения

Исправление мобильной навигации CMS-72 развёрнуто 25 ноября 2026 года: общий
`showPanel` снимает `cms-menu-open` до загрузки выбранного раздела управления.
Вызов остаётся внутри `guardUnsavedChanges`, поэтому отмена перехода сохраняет
редактор и меню. Типы материалов продолжают закрывать меню через
`selectContentType`; на ПК боковая панель остаётся видимой. Положительная
регрессия `tests/e2e/test_mobile_navigation.py` использует touch-ввод и профиль
iPhone 13; `--cms-browser webkit` выбирает движок для проверки Safari.

## 1. Назначение

Решение заменяет старую публичную часть MODX новым серверным сайтом и отдельной CMS. Старый сайт используется только как read-only источник миграции. Новые черновики, публикации, файлы, пользователи и заявки хранятся в новой системе.

Состав решения:

- публичный адаптивный сайт;
- схема-управляемый редактор CMS;
- редакционный workflow и история ревизий;
- медиатека с повторным использованием файлов;
- формы посетителей и очередь уведомлений;
- роли и управление сессиями;
- инструменты полного импорта и миграционной приёмки;
- двухфазный clean rollout: Windows формирует проверяемый source-bundle публичного MODX, Ubuntu импортирует его в staging и активирует только после schema/media/audit/preparation gate;
- поиск, SEO, sitemap, RSS и чистые публичные URL.

Чистая production-установка выполняется через проверяемый immutable
source-bundle: свежий Playwright-crawl публичного MODX, зеркалирование всех
обнаруженных файлов, import plan и missing-media evidence формируются отдельно
от production, фиксируются SHA-256 и проходят повторную проверку перед
staging-import. Runtime активируется только после schema 13, reconciliation,
post-apply audit и semantic verify.
На Windows используется отдельный preprod-root: чистый `release-checkout`,
изолированные `runtime`/Playwright/uv-кэши и `source-bundles` не пересекаются с
dev-checkout. Сборочный скрипт fail-closed отклоняет запуск из dev-каталога.
Media mirror различает постоянные 404/410, исчерпанные временные retry и fatal
errors. Незаконченный незапечатанный bundle можно безопасно продолжить: crawl
использует checkpoint, уже mirrored-файлы пропускаются, а отчёты и immutable
manifest строятся заново; sealed bundle остаётся неизменяемым.
На Ubuntu полная проверка bundle и staging-БД выполняется внутри собранного
application image с зафиксированными Python-зависимостями; системный Python
используется только для stdlib-проверок архива, окружения и manifest Git SHA.

## 2. Архитектура

| Слой | Реализация | Ответственность |
|---|---|---|
| HTTP-приложение | FastAPI | API, авторизация, workflow, публичные маршруты, фоновые задачи |
| Публичный render | Jinja2 | SSR-страницы с настоящими 200/404 и чистыми URL |
| CMS UI | HTML/CSS/vanilla JavaScript | Формы, блоки, preview, панели управления |
| Контентная схема | `site/cms-schema.json`, версия 1.7.0 | Типы, поля, блоки, порядок навигации |
| Хранилище | SQLite | Контент, ревизии, пользователи, заявки, медиа, аудит, редиректы |
| Файлы | `data/media` и `data/media-derivatives` | Оригиналы, thumbnails и WebP |
| Фоновые процессы | asyncio scheduler | Отложенные публикации, email-outbox, migration audit |
| Миграция | Python-модули `server/*import*`, `legacy_*`, `migration_*` | Crawl, импорт, зеркалирование, аудит и приёмка |

Приложение запускается одним FastAPI-процессом. Публичный сайт и CMS используют одну БД, поэтому опубликованная ревизия становится видимой без отдельной синхронизации.

## 3. Публичные маршруты

Основные SSR-маршруты:

- `/` — главная;
- `/schedule` — богослужения;
- `/about` — о храме;
- `/about/clergy/{slug}` — духовенство;
- `/parish` и `/parish/{slug}` — жизнь прихода;
- `/school` — воскресная школа;
- `/news` и `/news/{slug}` — новости;
- `/gallery` и `/gallery/{slug}` — фотоальбомы;
- `/leaflet` — выпуски листка;
- `/media` — видео и архив;
- `/pages/{slug}` — универсальные страницы;
- `/search` — поиск;
- `/sitemap.xml`, `/robots.txt`, `/rss.xml` — SEO/индексация.

Публичная detail-страница читает только `published_version` и `published_slug`. Рабочая версия может изменяться независимо и не попадает на сайт до следующей публикации.

## 4. Типы контента

CMS строит формы из схемы, а не из отдельных вручную написанных экранов.

| Тип | Назначение | Основное размещение |
|---|---|---|
| `home_feature` | Главные промо-блоки и содержание главной | `/` |
| `news` | Новости и анонсы | `/news/{slug}` |
| `service` | События расписания богослужений | `/schedule` |
| `gallery` | Фотоальбомы | `/gallery/{slug}` |
| `leaflet_issue` | Выпуски «Иннокентиевского листка» | `/leaflet` |
| `parish_section` | Направления приходской жизни | `/parish/{slug}` |
| `page` | Универсальные страницы | `/pages/{slug}` или тематический маршрут |
| `clergy` | Карточки духовенства | `/about/clergy/{slug}` |
| `video` | Видео и трансляции | `/media` |
| `site_contact` | Адрес, телефон, email и социальные сети | `/about#contacts`, футер |

Общие возможности полей:

- строка, многострочный текст, дата, время, число;
- select и checkbox;
- одиночное изображение/файл;
- список изображений;
- расписание из строк;
- список социальных ссылок;
- связи с другими материалами;
- SEO title, description и social image.

## 5. Блочная модель

Текстовое содержание хранится структурированным JSON-массивом блоков `{id, type, data}`. Произвольный HTML не принимается.

Поддерживаются:

1. `paragraph` — абзац с bold, italic и безопасными ссылками;
2. `heading` — структурированный заголовок;
3. `list` — маркированный или нумерованный список;
4. `image` — изображение, alt и подпись;
5. `gallery` — список изображений;
6. `quote` — цитата;
7. `video` — видео/трансляция;
8. `file` — документ для скачивания;
9. `callout` — информационная плашка.

Блок можно копировать, удалять и перемещать. Перед preview клиент проверяет обязательные данные image, gallery, video и file, показывает inline-ошибки и сохраняет последний успешный iframe. Валидный preview генерируется сервером тем же шаблонным слоем, что и публичная страница.

## 6. Модель контента и ревизий

Главные сущности:

- `contents` — текущее рабочее состояние и указатель на опубликованную ревизию;
- `revisions` — неизменяемые снимки версий;
- `audit_events` — журнал действий;
- `redirects` — старые пути и целевые чистые URL;
- FTS5-таблицы `content_search*` — полнотекстовый индекс.

Важные поля материала:

- `status`;
- `version` — версия рабочего состояния;
- `published_version` — версия, видимая посетителям;
- `slug` и `published_slug`;
- `scheduled_at`, `published_at`, `reviewed_at`, `deleted_at`;
- `migration_review_required`;
- `data_json` — значения схемы.

Каждая mutation передаёт ожидаемую `version`. Если другая сессия уже изменила объект, сервер возвращает 409 вместо тихого перезаписывания.

## 7. Редакционный workflow

```text
draft → in_review → published
  ↑        │          │
  │        ├→ scheduled ─→ published
  └────────┘          │
        restore ← archived/trash
```

Правила:

- редактор создаёт и сохраняет рабочую версию;
- редактор отправляет материал на проверку;
- publisher/admin возвращает, публикует сразу или назначает дату;
- scheduler публикует наступившие `scheduled`-материалы;
- архив и корзина скрывают публичную страницу;
- восстановление создаёт снова скрытый черновик;
- восстановление ревизии копирует старые данные в новую рабочую версию;
- опубликованная версия остаётся доступна, пока новая рабочая версия редактируется.

Редакционная очередь выполняет массовую публикацию и архивирование атомарно: при конфликте не меняется ни один выбранный объект.

Клиент различает сохранение черновика и готовность к смене статуса. Неполный черновик разрешено сохранять, но перед `submit-review`, `schedule` и `publish` интерфейс вычисляет обязательные поля по схеме, показывает сводку, назначает `aria-invalid` и переводит фокус к первому пропуску. Невалидный workflow-запрос на сервер не отправляется; серверная `require_ready` остаётся вторым уровнем защиты.

Dirty-состояние редактора защищено единым navigation guard с вариантами сохранить, отбросить или остаться; для закрытия и перезагрузки используется `beforeunload`. При истечении сессии DOM редактора сохраняется, защищённые действия блокируются, а после повторного входа пользователь продолжает работу с теми же значениями.

## 8. Роли и безопасность доступа

Роли образуют возрастающую иерархию:

| Роль | Права |
|---|---|
| `viewer` | Просмотр материалов, истории, медиатеки и migration dashboard |
| `editor` | Viewer + создание/редактирование, загрузка медиа, отправка на проверку, решения по draft-партии |
| `publisher` | Editor + публикация, расписание, архив/корзина, массовые действия, заявки, аудит, preview автоматической подготовки и финализация миграции |
| `admin` | Publisher + apply/rollback автоматической подготовки, пользователи, завершение сессий, reindex и удаление неиспользуемых файлов |

Сессии хранятся сервером и используют CSRF-token для mutation. Смена пароля завершает все сессии пользователя. Администратор может отдельно отозвать чужие сессии, заблокировать учётную запись или изменить роль.

Development-пароль `temple-demo` активен только при `CMS_ENV=development`. В production должен быть задан длинный `CMS_BOOTSTRAP_PASSWORD` до первого запуска.

## 9. Медиатека

Таблица `media` хранит метаданные оригинала, checksum, MIME, размер, тип, alt, версию и источник. `media_usages` связывает файл с рабочими и историческими версиями материалов.

Возможности:

- поиск по имени, alt и использующему материалу;
- фильтры image/video/document и used/unused;
- пагинация по 48 объектов;
- повторное использование без создания копии;
- постоянный URL оригинала;
- thumbnails/WebP для изображений;
- изменение alt;
- replacement как новый media object вместо перезаписи старого;
- удаление только неиспользуемого файла администратором;
- долговечный фоновый reindex существующего каталога с фазами, прогрессом, счётчиками и журналом ошибок;
- детерминированная сверка manifest, файловой системы, реестра, производных, ссылок материалов и missing-media отчёта;
- отдельный список потерянных legacy-файлов.

Ограничения размеров и допустимые расширения задаются переменными `CMS_MAX_*_BYTES` и серверной валидацией реального типа файла.
Пользовательская загрузка GIF запрещена. Исключение сделано только для
зеркальных файлов `legacy/*.gif`: индексатор принимает корректный одно-кадровый
GIF после Pillow-верификации, помечает его как `image/gif` и сохраняет признак
`legacy_static_gif`. Анимированный, повреждённый или находящийся вне `legacy/`
GIF остаётся невалидным.
Для зеркальных JPG/PNG/WebP действует аналогичная узкая совместимость с
источником: после полной проверки байтов индексатор может сохранить обнаруженный
MIME при исторически неверном suffix и записывает
`legacy_extension_mismatch`, исходное и обнаруженное расширения. Этот путь
недоступен upload API. Clean bootstrap и post-activation verify требуют, чтобы
итоговая media reconciliation имела `status=ok` и `unexplained_count=0`.

Задачи reindex хранятся в `media_reindex_jobs`. В один момент времени разрешена одна активная задача; после перезапуска незавершённая задача возвращается в очередь. `POST /api/admin/media/reindex` отвечает `202`, а состояние доступно через `GET /api/admin/media-reindex` и `GET /api/admin/media-reindex/{job_id}`. Применение найденных изменений выполняется одной SQLite-транзакцией; пути файловой системы и секреты в ошибках API редактируются.

Миграция схемы 11 добавляет `media_reindex_jobs.reconciliation_json`. После индексирования сервер сохраняет классификацию:

- URL manifest, уникальные stored paths, группы алиасов и отсутствующие оригиналы;
- физические файлы, объекты вне manifest и зарегистрированные записи без файла;
- количество и валидность производных, включая сиротские cache-файлы;
- все `/media/`-ссылки из текущего `data_json` и исторических `revisions.snapshot_json`;
- пропущенные и устаревшие строки `media_usages`;
- множества URL из manifest errors, CSV-отчёта и `missing_media_issues`;
- безопасные относительные samples и суммарный `unexplained_count`.

Dry-run открывает SQLite через URI `mode=ro`. Явный apply использует существующий идемпотентный индексатор: регистрирует физические файлы, импортирует missing issues и перестраивает использования. Он не удаляет и не заменяет оригиналы. Для актуального источника доказаны формулы `13 746 = 13 698 + 48` URL/уникальные/алиасы и `13 699 = 13 698 + 1` физические/manifest/вне manifest; 201 отсутствующий legacy-URL согласован во всех трёх реестрах.

## 10. Заявки посетителей

Поддерживаются два типа:

- `prayer_note` — вид поминовения и 1–10 имён;
- `school_enrollment` — родитель, контакт, ребёнок, возраст, комментарий и согласие.

Сначала заявка записывается в SQLite и получает reference code. Затем `notification_outbox` независимо пытается отправить email. Поэтому ошибка SMTP не теряет обращение.

Статусы обработки: `new`, `in_progress`, `done`, `spam`. История переходов записывается в `submission_events`. Закрытые записки очищаются через 30 дней, школьные обращения — через 180 дней.

Защита форм:

- серверная валидация;
- honeypot;
- rate limit по HMAC-хешу IP;
- исходный IP не сохраняется;
- доверенные proxy-сети задаются явно;
- персональные данные не входят в list-response, а открываются только в карточке.

## 11. Миграция и приёмка

Миграционный pipeline:

1. read-only crawl старого сайта;
2. инвентаризация URL и медиа;
3. зеркалирование файлов с SHA-256 и checkpoint;
4. идемпотентный импорт черновиков;
5. создание 301-редиректов;
6. автоматический audit;
7. детерминированный preview и автоматическая подготовка;
8. редакционные партии только для содержательно неоднозначного остатка;
9. атомарная финализация решений.

Audit проверяет обязательные поля, даты, кодировку, HTML/служебный текст, media, alt, внутренние и внешние ссылки, дубли и provenance. Уровни: blocker, warning, info.

Выдача проблем ищет по коду, заголовку, старому URL и сообщению. Клиент отменяет устаревшие запросы dashboard и применяет только последний ответ, поэтому быстрое переключение фильтров не может вернуть интерфейс к старому состоянию.

При переходе **«Исправить»** клиент фиксирует применённые фильтры, offset,
идентификатор и индекс issue, прокрутку и opener. Кнопка контекстного возврата
и пункт **«Миграция»** повторно строят dashboard из этого состояния и возвращают
клавиатурный фокус исходной строке. После сохранения issue прежней версии больше
не входит в актуальную выдачу, поэтому используется ближайшая строка той же
страницы; если страница стала пустой, offset безопасно сдвигается к последней
существующей странице. Для редакционной партии сохраняются ID партии и
материала. Обычный переход к другому типу или административной панели очищает
контекст, чтобы позднее не выполнить неожиданный возврат.

Схема БД 12 добавляет `migration_preparation_runs` и `migration_preparation_items`. Preview фиксирует правила, audit run, рабочую версию и SHA-256 нормализованной версии «до», затем сохраняет предложенную версию, список преобразований, причины, рекомендацию и варианты редакционного решения. Классы:

- `auto_ready` — формальные правила достаточны;
- `editorial_review` — остаётся вопрос, способный изменить содержание;
- `technical_blocker` — программная или структурная проблема, которую нельзя перекладывать на редактора.

Apply разрешён только администратору и только для завершённого preview. Перед первой записью весь набор повторно проверяется по version/hash; устаревший preview отклоняется без частичного применения. Изменения создают системные ревизии, audit events, обновляют media usages и FTS. Материалы остаются в прежнем workflow-состоянии, не публикуются, а `migration_review_required` остаётся равным единице. Повторный apply идемпотентен. Rollback создаёт компенсирующие ревизии и останавливается, если редактор уже изменил хотя бы один затронутый материал.

Детерминированные правила включают Unicode NFKC, удаление управляющих символов и crawl chrome, преобразование legacy-текста в блоки, краткое описание из содержательного текста, доказуемое восстановление даты, alt из заголовка, нормализацию повторяемых фотографий, перенос provenance в журнал и обложку выпуска из первой страницы доступного PDF. Неоднозначная дата, дубли содержания и отсутствующая содержательно подходящая замена медиа остаются в `editorial_review`.

Партия фиксирует конкретные версии материалов и результатов аудита. Для каждого объекта редактор выбирает `accept`, `archive` или `trash`, отмечает ручной просмотр и подтверждает индивидуальные warnings. Publisher подтверждает общие warnings и финализирует атомарно. При конфликте версии вся операция останавливается.

Финализация миграции не публикует материалы: она снимает migration-флаг или переводит объект в выбранное непубличное состояние. Публикация остаётся отдельным workflow.

## 12. Поиск и SEO

Поиск использует SQLite FTS5 по заголовкам, описаниям и текстовым блокам опубликованных ревизий. Публичные страницы получают:

- уникальный `<title>` и description;
- canonical URL;
- Open Graph;
- social preview;
- JSON-LD;
- sitemap и RSS.

Production deployment должен включать согласованный SQLite backup, копию `data/media`, проверку восстановления, миграции схемы, readiness и smoke-тест. Порт приложения предназначен для loopback; наружу сайт публикуется через HTTPS reverse proxy.

# Анализ новых правил архива и дат — 24 ноября 2026 года

`python -X utf8 -m server.migration_analysis` создаёт прогноз в
`outputs/migration-policy-analysis.json` и `.md`. Это отдельный технический CLI;
он не вводит нового пользовательского API или ролевого действия CMS.

Источник открывается через SQLite URI `mode=ro` и копируется Online Backup API
с учётом WAL. Миграции схемы, сверка медиа, подготовка, создание PDF-обложек,
изменение статусов/флагов и повторный аудит выполняются только на временной копии.
Оригиналы медиа копируются hardlink либо обычным копированием; существующие
файлы не перезаписываются. До/после сравниваются логический SHA-256 таблиц SQLite,
инвентарь файлов и SHA-256 manifest. Отчёт возвращает `source_unchanged`;
при расхождении CLI завершается с кодом 2.

Область анализа: вся миграционная очередь после обновления схемы копии и активные
фотоальбомы, которые новое правило исправляет или возвращает в очередь. Архивные
и удалённые альбомы повторно не открываются. Новости и анонсы представлены типом
`news`, дата — `publication_date`; фотоальбомы — `gallery`, дата — `event_date`.
Разница исходной очереди и очереди после schema показывается отдельно.

Классификация выполняется после проекции существующей подготовки и новых правил.
`archive`, `ready_for_publication`, `remaining_queue` — непересекающиеся исходы.
`corrected_and_ready` входит в готовые, `corrected_total` пересекается с остатком
очереди. Исправлением считается изменение данных, включая техническую нормализацию
и фиксацию точности даты. Условное 1 января имеет точность `year`: это
признак происхождения, но по политике v2 не является причиной очереди.
Настоящее подтверждённое 1 января имеет точность `day`.

Готовность — прогноз возможности миграционной приёмки и обычного workflow публикации
после применения и повторной проверки; анализатор сам не снимает рабочий флаг и
не публикует. Незавершённая партия и неподходящий workflow-статус показываются как
самостоятельные причины. Неполные обязательные поля относятся к содержательным
вопросам; технические ошибки и непроверенные внешние ссылки выделяются отдельно.

`remaining_reasons` содержит каждую причину, уникальные материалы, число замечаний,
поля, типы и все ID. `reason_combinations` даёт непересекающиеся группы с суммой,
равной остатку очереди. Список `items` не обрезается и содержит заголовок, URL,
старую/предлагаемую дату, точность, преобразования и причины каждого материала.

По умолчанию используется только свежий внешний cache: отсутствие/просрочка
не скрывается и не засчитывается как успешная проверка. `--check-external`
разрешает сетевой аудит на копии. Параметры источника: `--database`, `--media`,
`--manifest`, `--missing-report`; выходов — `--json`, `--markdown`; временного каталога — `--work-root`.
Отчётами запрещено перезаписывать источник, SQLite sidecar, manifest, CSV и schema
или записывать их внутрь исходной медиатеки.

Покрытие CLI и чистых правил зарегистрировано в `tests/e2e/coverage.json:analysis_suites`;
реальные данные — в source-data тесте `test_migration_policy_analysis_on_source_copy`.
Для CLI без сессии CMS ролевые UI-переходы неприменимы; существующие роли и browser
workflow продолжают проверяться полным Playwright-набором.

## Действующая политика v2

Последнее уточнение пользователя отменяет возрастной отбор: архивируется весь
тип `news` с миграционным флагом, включая анонсы и неопределённые даты.
Публикация не выполняется; при проекции архива содержимое и историческая дата
не переписываются. Новости вне очереди и корзина не подхватываются правилом.

Для `gallery` дата с 01.01 и известным годом считается допустимой. Год URL
приоритетен; точность `year` и версия политики фиксируются в данных.
В подготовке 1.3.0 сохраняются все фото и относительный порядок, включая повторы;
пустой alt можно заполнить заголовком без изменения состава коллекции.
`photo_collection_policy=preserve_all` документирует принятое правило повторов.
Аудит 1.2.0 не требует проверки таких повторов, но проверяет действительность файлов.
Реальный 2000 год, подтверждённый URL и версией политики, отличается от заглушки.

CMS-62 устраняет ложный `text_extraction_ambiguous` для полей, которых нет в схеме.
Это исправление функциональности подготовки, а не автоматическое признание любого
текста корректным. Обязательные поля, источники без определимого года, конфликтующие
день/месяц и независимые замечания остаются в аудите.

Анализатор сверяет число и последовательность всех фото до и после проекции;
расхождение останавливает расчёт. Сводка показывает оба количества и
`gallery_all_photos_preserved`. Старый `--archive-before` удалён, чтобы отчёт
не воспроизводил отменённую политику. Применение preview старой версии блокируется
ошибкой `PREVIEW_RULES_CHANGED`. Сам анализатор по-прежнему не изменяет источник.
# Исполняемая процедура миграционной политики

Модуль `server.migration_procedure` реализует `plan`, `apply`, `verify`, `status`,
`rollback`; пошаговая инструкция — `cms-migration-policy-procedure.md`.
Схема 15 не расширяется: полные исходные снимки и hashes записанных строк
сохраняются в `audit_events`, редакции — в `revisions`, происхождение и удержание
генерируемых файлов — в `media_events`.

План содержит отдельные backup, проекцию и отчёт, контрольные суммы, срок 24 часа
и точный target. Исполняемые поля сверяются с проекцией и исходным снимком.
БД, медиа и manifest повторно проверяются до первой записи под блокировкой SQLite.
Изменения контента, индекса, связей и журнала фиксируются одной транзакцией;
публикация отсутствует. Новые файлы проверяются отдельно и восстанавливаются
после прерванной установки без дублирования. Повторный запуск определяет фазу
по журналу БД. Межпроцессная блокировка освобождается после аварии ОС.

Проверка принятых черновиков, обычная подготовка остатка без новых изменений,
post-audit, semantic verify и сверка медиа обязательны. При неуспешном postcheck
выполняется автоматический откат, если строки не менялись позже. При конфликте
последующая правка сохраняется и возвращается отдельная структурированная ошибка.
Откат сохраняет версии и файлы истории, восстанавливает исходные поля и выполняет
аудит. Нативные черновики защищены отдельной регрессией CMS-63.

## Мобильный вход в просмотр сайта с черновиками

При ширине до 760 px ссылка «Сайт с черновиками» находится в начале бокового
меню CMS. На компьютере используется прежняя верхняя ссылка. Оба элемента

`updateSessionUi` и `guardUnsavedChanges` и скрываются без действующей сессии.
Постоянная регрессия CMS-74 проверяет все четыре роли на 390/320 px, отсутствие
переполнения, возврат в CMS, видимость ссылки на ПК, выход и три решения по
несохранённым изменениям. Браузеры: Chromium и WebKit с touch-профилем iPhone.
