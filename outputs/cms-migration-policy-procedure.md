# Процедура применения миграционной политики v2

Дата: 24 ноября 2026 года. Код: `server/migration_procedure.py`.

Production-бэкап должен содержать фактические `data/missing-legacy-media.csv`
и `data/missing-legacy-media.md`, если они используются runtime. Сверка после
восстановления использует этот CSV; файл из checkout может относиться к другому
снимку. Начиная с исправления CMS-64 стандартный backup/restore gate сохраняет
эти отчёты и проверяет их контрольные суммы.

## Назначение и границы

Процедура применяет согласованные правила к существующей CMS:

1. Все новости и анонсы из миграционной очереди, включая недатированные,
   переводятся в `archived`. Миграционный флаг снимается. Исходные текст,
   фотографии и дата новости сохраняются. Публикация и расписание отключаются.
2. В мигрированных альбомах сохраняются все фото, их последовательность,
   подписи и повторные ссылки. Год корректируется по однозначному URL.
   При отсутствии дня и месяца используется допустимое `01.01` этого года.
3. Материалы, прошедшие все проверки, становятся принятыми черновиками:
   `status=draft`, `migration_review_required=0`, `published_version=NULL`.
   Публикация выполняется впоследствии обычным workflow CMS.
4. Материалы с независимыми содержательными замечаниями сохраняют миграционный
   флаг. Процедура не выбирает канонический дубль, не выдумывает неизвестный год
   и не заполняет содержательные обязательные поля предположениями.
5. Нативные черновики без legacy identity и миграционного флага не затрагиваются.
   Корзина не восстанавливается. Фото и старые редакции не удаляются.

Схема БД остаётся 15. Политика: `2026-11-v2`; подготовка: `1.3.0`; аудит: `1.2.0`.
Используются существующие `audit_events`, `revisions`, `media_events` и контур
подготовки/семантической проверки. Отдельной таблицы или хранимой процедуры SQL нет.

## Условия начала

- На целевом runtime развёрнут проверенный релиз с этим модулем. Схема и её
  checksums актуальны, `quick_check=ok`, нарушений внешних ключей нет.
- Медиа-реестр и manifest согласованы: `status=ok`, `unexplained_count=0`.
- Фоновые задания завершены. Затрагиваемые материалы не входят в незавершённые
  редакционные партии. Чужая незавершённая работа не отменяется автоматически.
- Сервис CMS и другие писатели остановлены до создания плана и остаются
  остановленными до завершения проверки. Это техническое окно обслуживания;
  отдельные содержательные подтверждения уже однозначных правил не нужны.
- Оператор имеет доступ к runtime-файлам и явно указывает активную учётную запись
  администратора или выпускающего для полномочий и журнала. Это технический CLI,
  а не сетевой способ входа в CMS.
- Для каталога операции есть место под исходную SQLite-копию, проверенную проекцию
  и новые PDF-обложки. Каталог расположен вне runtime-хранилища и не публикуется:
  SQLite-backup содержит в том числе внутренние таблицы пользователей и сессий.

Процедура сама не обновляет рабочую схему и не разворачивает релиз. Не следует
собирать или перетегивать production-образ во время baseline; используется
существующий release/restore gate из `cms-production-clean-migration-guide.md`
и `scripts/production_apply_stage15.sh`.

Локальный `data/cms.sqlite3` проекта является исходником без применённой схемы.
Применять процедуру непосредственно к нему нельзя: он используется source-data
проверками. Репетиция выполняется на отдельной копии, production — по свежему
плану именно целевого runtime.

## Состояния операции

| Состояние | Значение | Следующий шаг |
|---|---|---|
| План в каталоге, `not_applied` в журнале | Источник ещё не изменён | Проверить сводку и применить этот план |
| `applied` | Транзакция записана; итоговая проверка ещё не завершена | Повторить `apply` с тем же каталогом либо `verify` |
| `verified` | Аудит, semantic gate и сверка медиа прошли | Сохранить receipt, запустить CMS |
| `rolled_back` | Данные материалов восстановлены из журнала | Проверить результат; для новой попытки создать новый план |
| `no_changes` | Исполняемых изменений нет | Применять нечего |

Одновременно допускается одна изменяющая процедура на runtime. Межпроцессная
блокировка освобождается операционной системой после завершения или аварии;
удалять «зависший PID» вручную не требуется.

## 1. Создать план

Пример PowerShell для отдельного runtime. Пути заменяются на фактические; исходный
dev-файл проекта не используется.

```powershell
$cmsPython = 'C:\Projects\temple\.venv\Scripts\python.exe'
$cmsProcedureArgs = @(
  '--database', 'C:\CMSRuntime\data\cms.sqlite3',
  '--media', 'C:\CMSRuntime\data\media',
  '--manifest', 'C:\CMSRuntime\data\legacy-media-manifest.json',
  '--missing-report', 'C:\CMSRuntime\missing-legacy-media.csv'
)
$cmsBundle = 'C:\CMSOperations\policy-v2-20261124'

& $cmsPython -X utf8 -m server.migration_procedure plan @cmsProcedureArgs --bundle $cmsBundle
```

Каталог должен быть новым. `plan`:

- открывает источник read-only и делает SQLite Online Backup с учётом WAL;
- на копии рассчитывает исправления, архив и причины остатка очереди;
- создаёт и проверяет необходимые PDF-обложки только в каталоге операции;
- повторяет аудит проекции и сверяет неизменность источника;
- сохраняет полный состав изменений и SHA-256 артефактов.

Каталог содержит:

| Файл | Содержимое |
|---|---|
| `plan.json` | ID операции, срок, target, исходный fingerprint, версии, строки до/после, файлы, seal |
| `report.md`, `report.json` | Числа, все причины и перечень материалов |
| `baseline.sqlite3` | Проверенная исходная копия БД |
| `projection/projected.sqlite3` | Проекция, по которой сверяются исполняемые изменения |
| `projection/media/generated/...` | Только новые генерируемые обложки |

План действителен 24 часа. Любое изменение БД, инвентаря медиа или manifest делает
его устаревшим. Поэтому нельзя входить в CMS, редактировать данные или запускать
новый аудит между `plan` и первым `apply`. Контрольные суммы защищают от повреждения
и рассогласования артефактов; каталог остаётся в распоряжении доверенного оператора.

Без `--check-external` используются только свежие сведения о внешних ссылках.
Отсутствующая/просроченная проверка не считается успешной. При технических блокерах
исполняемый план не создаётся: сначала исправляется техническая причина.

Для известного локального снимка контрольный прогноз составляет:
**732 архив / 576 принятых черновиков / 449 в очереди; 10 869 фото сохранены**.
Это не константы production: рабочий runtime рассчитывается заново, а затем
применяется именно состав его плана.

## 2. Применить тот же план

```powershell
& $cmsPython -X utf8 -m server.migration_procedure apply @cmsProcedureArgs --bundle $cmsBundle --actor-user admin
```

Перед записью проверяются полномочия, версии правил, seal и все файлы, соответствие
исполняемых строк отдельной проекции, срок, target, полный fingerprint исходника,
версии и hashes материалов, отсутствие активных редакционных партий.

Под `BEGIN IMMEDIATE` создаваемые файлы устанавливаются без изменения оригиналов,
затем **одной транзакцией** записываются реестр новых файлов, материалы, новые
редакции, статусы старых замечаний, поисковый индекс, связи медиа и журнал операции.
При сбое SQL частичного изменения материалов нет. В журнале каждой строки
сохраняются исходный полный снимок и hash записанного состояния.

Ни один шаг не вызывает публикацию. Согласованные черновики только освобождаются
от миграционного флага; непроверенные материалы остаются в очереди.

После commit автоматически выполняются:

1. Аудит всех активных материалов и проверка нулевых blocker/warning у принятых
   черновиков из плана.
2. Аудит остатка очереди и его регистрация в обычном контуре подготовки. Если
   повторная подготовка предлагает новые изменения, не вошедшие в план, применение
   откатывается; новые исправления без анализа не добавляются.
3. Полный post-audit, semantic verify и сверка медиа.
4. Повторная проверка hashes строк и создаваемых файлов.

Успех возвращает `status=verified`, `semantic_ok=true`, `media_ok=true`.
Результат записывается в `receipt.json` в каталоге операции.

## 3. Проверить статус или продолжить после остановки

`operation_id` берётся из вывода `plan` или `plan.json`, без поиска ID материалов.

```powershell
$cmsOperation = (Get-Content -LiteralPath (Join-Path $cmsBundle 'plan.json') -Raw | ConvertFrom-Json).operation_id
& $cmsPython -X utf8 -m server.migration_procedure status @cmsProcedureArgs --operation-id $cmsOperation
& $cmsPython -X utf8 -m server.migration_procedure verify @cmsProcedureArgs --operation-id $cmsOperation --actor-user admin
```

Повторный `apply` с тем же каталогом также допустим:

- до commit исходные строки проверяются и записываются целиком;
- после commit запись материалов не повторяется — продолжается проверка;
- после успешной проверки возвращается `replayed=true` без новой редакции;
- после отката этот ID повторно не применяется.

Установленные перед аварией, но ещё не зарегистрированные обложки узнаются по
плану и hash; повторное создание не дублирует их. Временные файлы этой операции
очищаются адресно. Незавершённые задания проверки именно этой операции
журналируются как прерванные и заменяются новой проверкой. Журнал БД является
источником состояния, даже если процесс не успел записать `receipt.json`.

## 4. Откат

```powershell
& $cmsPython -X utf8 -m server.migration_procedure rollback @cmsProcedureArgs --operation-id $cmsOperation --actor-user admin
```

Откатывается только последняя операция, если ни одна её строка не изменена позже.
Проверка всех строк выполняется до первого восстановления. Чужая правка, включая
изменение без увеличения версии, блокирует весь откат.

В одной транзакции восстанавливаются содержимое, дата, полный список фото,
статусы, миграционные флаги и прежние публичные указатели. Номера версий продолжают
расти: история не переписывается. Если новость была публичной до операции, откат
восстанавливает именно её прежний опубликованный snapshot.

После восстановления выполняется новый аудит. Сгенерированные файлы и их
реестр сохраняются, поскольку на них могут ссылаться исторические редакции;
сохранение при откате отдельно журналируется. Оригиналы не удаляются.

Повторный откат возвращает `replayed=true`. Восстановление материалов не означает
автоматического принятия восстановленной очереди: при необходимости её досье
заново проходит обычную подготовку и gate до следующей приёмки.

## Ошибки и остановка

| Код | Значение и действие |
|---|---|
| `SCHEMA_NOT_READY`, `MEDIA_NOT_READY` | Сначала выполнить штатную техническую подготовку runtime |
| `BACKGROUND_WORK_ACTIVE`, `ACTIVE_BATCH` | Не вмешиваться в незавершённую работу; привести runtime к условиям окна обслуживания |
| `PLAN_STALE`, `PLAN_EXPIRED`, `RULES_CHANGED` | Создать новый план; не править JSON для обхода проверки |
| `PLAN_TAMPERED`, `BUNDLE_TAMPERED`, `PLAN_INVALID` | Использовать неповреждённый каталог либо создать новый |
| `OPERATION_BUSY` | Дождаться другой процедуры; блокировку принудительно не снимать |
| `CONTENT_CHANGED` | Последующая правка сохранена; автоматический откат запрещён |
| `POSTCHECK_FAILED_ROLLED_BACK` | Итоговый контроль не прошёл, материалы автоматически восстановлены |
| `POSTCHECK_FAILED_ROLLBACK_BLOCKED` | Не запускать CMS поверх непроверенного результата; использовать журнал и baseline в штатном restore-контуре |

При блокировке отката нельзя принудительно перезаписывать рабочую БД или её WAL.
Оператор сохраняет журнал и каталог операции и использует существующий
проверенный backup/restore процесс. Решение по содержанию требуется только при
реальном конфликте редакционных правок, а не для выполнения технических команд.

## Docker/Ubuntu

Сервис проекта называется `cms`. Обычный контейнер останавливается до плана.
Проверенный образ запускает CLI отдельным контейнером с тем же `/data` и отдельным
постоянным приватным каталогом `/operations`; пути manifest/CSV передаются явно
или берутся из принятого окружения релиза. Не используется ephemeral output
внутри удаляемого контейнера.

```bash
docker compose stop cms
docker compose run --rm --no-deps -v "$PWD/operations:/operations" cms \
  python -m server.migration_procedure plan --bundle /operations/policy-v2
docker compose run --rm --no-deps -v "$PWD/operations:/operations" cms \
  python -m server.migration_procedure apply --bundle /operations/policy-v2 --actor-user admin
```

Сервис запускается обратно только после `verified` и сохранения receipt.
Для возврата используется существующий проверенный container/release workflow;
образ не пересобирается и не меняется между plan/apply/verify/rollback.

## Приёмка разработки

Постоянные проверки находятся в `tests/test_migration_procedure.py`, source-data
сценарии `test_migration_procedure_apply_verify_and_rollback_on_source_copy` и
Playwright-сценарии `test_policy_procedure_history_labels`.

Обязательны серверные тесты, smoke, полный регресс и source-data с единственным
ожидаемым содержательным `GAP-01`. На реальной копии проверяются применение,
нулевая новая публикация, все фото и их порядок, semantic/media gate, повторный
запуск и восстановление исходных полей при монотонных версиях. Исходная runtime-БД,
медиатека и manifest подтверждаются как неизменённые.

Фактическая приёмка завершена 24 ноября 2026 года: server 231/231,
smoke 3/3, два full-прогона 52/52 с 378 assertion ID, source-data 10 проверок
с единственным ожидаемым GAP-01. Полный цикл применения, проверки и отката
прошёл на реальной копии. Evidence: `cms-migration-policy-procedure-verification.md`.
